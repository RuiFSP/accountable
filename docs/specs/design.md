# Spec: Design

## Architecture

- **Backend** (`backend/`): Python 3.12, FastAPI, SQLAlchemy Core. `npm start` reads `.env` — `DATABASE_URL`, `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` — and runs against Postgres on Supabase; `npm run dev` leaves those settings out and keeps its own database on this computer, so it never reaches Supabase. The sign-in is checked on every request. Row-level security is on for every table, so Supabase's Data API — which the publishable key can reach — serves nothing; the app talks to Postgres directly. Seeds sample data when the database is new. `npm run seed` drops and recreates it, asking for confirmation first. The PDFs bring one dependency, a pure-Python PDF library installed with uv like the rest, so Render's native Python runtime needs no system packages.
- Row-level security is on for every table with no policies, deliberately: with nothing allowed through, the Data API returns no rows. Supabase's security advisor reports `RLS Enabled No Policy` on every table for exactly that reason, and writing a policy there would open the Data API up rather than close a hole. The tables are owned by `postgres`, and a table's owner is not subject to row-level security, so the app's own queries are unaffected.
- **Frontend** (`frontend/`): React + Vite + TypeScript, talks to the backend JSON API. In Supabase mode the browser holds only the publishable key; signed out, every route shows the sign-in screen.
- **Shared code** lives above the areas on both sides. On the backend, `backend/app/records.py` holds `read_or_404` (one row, or a 404 naming the record), `require_exists` (a link to a missing record is a 400), `stamp_created` (an add records who added it and who last changed it) and `stamp_updated` (a save records who last changed it only when a stored value actually differs); `tax.py` works out a line's amount, the subtotal, the tax and the total; `documents.py` reads the company settings and gives a quote or an invoice its next number; `holds.py` refuses to delete a deal or an organization while another area's records point at it — the bills router registers the bill's supplier link there, so an organization with bills can't be deleted; `months.py` gives every monthly chart the same 12 buckets; `stages.py` holds the board's move rules — the new stage's probability, the place at the end of the column, the renumbering and the timeline entry — so a drag and a quote's accept cannot drift apart; `quote_pdf.py` builds a quote's document and renders it on the server when its download is asked for, from the quote's saved values, with fpdf2 — a pure-Python library installed by uv with no system packages, so Render runs it as it is — drawing every string as text with the three brand fonts (Instrument Serif, Instrument Sans and JetBrains Mono) as TTF files kept beside the backend code, assets rather than dependencies, since the frontend's woff2 copies cannot be embedded; `invoice_pdf.py` draws an invoice's PDF in its chosen design; and `images.py` checks an uploaded logo's real type. The routers in `backend/app/routes/` keep only their own area's schema and rules: `bills.py` holds the bill's fields, its paid and unpaid actions and its bill-number rule. On the frontend, shared UI lives in `frontend/src/components/`: the forms (`DealForm`, `ContactForm`, `OrganizationForm`, `ProductForm`, `InvoiceForm`, and `ActivityForm` inside `Timeline.tsx`), `InvoicePreview` (the document, shared by the invoice form and the Settings sample), the quote's `QuoteDocument` and `QuoteForm`, `DataTable`, the dialogs, `KpiCard`, `StatusBadge`, `RecordAttribution` and `RecordPanels`; generic helpers live in `frontend/src/lib/`, including `tax.ts`'s copy of the document sums for the live preview, `invoice.ts` for an invoice's status, balance and aging, and `bills.ts` for the bill categories and status; `frontend/src/pages/` holds only each area's own pages, with `pages/money/` holding the three tabs' pages, the quote pages, the bills list, its form and the panels the quotes, invoices and bills changes add to deal and organization pages, registered in `routes.tsx` like every area's.
- **Commands** (root `package.json`): `npm run dev`, `npm start` (builds the frontend and runs the app the way Render does), `npm test`, `npm run seed`. Tests: Vitest (frontend), pytest (backend), Playwright in `e2e/` on installed Chrome; tests use their own SQLite databases, each end-to-end run takes ports no other run is using, and no more than two test runs go at once on this computer — the rest wait their turn and say so — so `npm run check` can run in three worktrees at once. The end-to-end tests sign in without anyone's real password and never touch Supabase, so CI needs no secrets.
- **Deployment**: Render's free plan as one web service — FastAPI serves the built frontend and the API, migrations run when it starts. Described by `render.yaml`, with the Supabase settings entered in Render, not written in the file; see [Running it](running.md).

## Data model

| Table | Fields |
|---|---|
| organizations | id, name, website, industry, notes, billing_address |
| contacts | id, name, email, phone, job_title, organization_id, status |
| deals | id, name, organization_id, contact_id, stage, value_cents, probability, close_date, position |
| activities | id, type (note, call, email, stage_change), contact_id?, deal_id?, description, happened_at, follow_up_date?, done |
| products | id, name, description, price_cents, active |
| bills | id, organization_id, bill_number, bill_date, due_date, category, amount_cents, tax_cents, total_cents, notes, paid_date |
| company_settings | id, name, address, email, phone, tax_label, tax_rate_thousandths, payment_terms_days, quote_prefix, invoice_prefix, invoice_design, accent_color, logo_data?, logo_content_type?, updated_by, updated_at |
| number_counters | id, kind (quote or invoice), last_number |
| quotes | id, number, deal_id, status (draft, sent, accepted or declined), created_at, valid_until, tax_label, tax_rate_thousandths |
| quote_lines | id, quote_id, product_id, product_name, description, quantity, unit_price_cents, position |
| invoices | id, number?, deal_id, organization_id, status (draft, issued, void), issue_date?, due_date?, subtotal_cents, tax_label?, tax_rate_thousandths?, tax_cents?, total_cents?, bill_to_name?, bill_to_address?, bill_to_contact_name?, bill_to_contact_email?, created_by, updated_by |
| invoice_lines | id, invoice_id, product_id?, description, quantity, unit_price_cents, position |
| payments | id, invoice_id, paid_on, amount_cents, method (bank_transfer, card, check, cash, other), reference?, created_by |

- Every record table also records who added the row and who last changed it: `created_by` and `updated_by`, holding the signed-in user's email as it comes from the checked token. Both show on the record's detail page — on a quote's and an invoice's page too — and products have no detail page, so both show in the Products table, and a bill has none either, so both show in its add and edit dialog. A payment records who entered it in its own `created_by` and shows it beside the payment.
- `bills.organization_id` is the supplier: an organization, with no customer or supplier flag on the organization itself, so one company can be both. `bill_number` is required and unique for its supplier, trimmed and compared ignoring case in Python, so SQLite and Postgres answer the same.
- `bills.total_cents` is `amount_cents` plus `tax_cents`, written by the backend and never taken from the browser. The amount and the tax are whole cents as the supplier's bill has them; the company settings' tax rate is not used on a bill.
- `bills.paid_date` is empty while a bill is unpaid and holds the day it was paid otherwise. There is no status column: a bill is overdue when it is unpaid and its `due_date` is before today, and marking a bill unpaid clears the date. A new bill's due date starts 30 days after its bill date, and the form can send any date.
- `company_settings` holds one row for the team, with `updated_by` and `updated_at` for who last changed it and when. The tax rate is stored as an integer number of thousandths of a percent (`tax_rate_thousandths`), so 8.875% is 8875; payment terms are whole days. `invoice_design` is one of `classic`, `modern` or `compact`, `accent_color` a hex color such as `#073B4C`, and `logo_data` and `logo_content_type` hold the uploaded logo or stay empty.
- `number_counters` holds one row for each kind of document that has taken a number, added when it takes its first. Quotes and invoices count apart, and a reset clears the rows so each count starts at 1.
- A quote belongs to one deal, carries the day it was created and its valid-until date, and keeps the tax label and rate it was sent with; a draft reads them from the settings instead. Expired is not stored: a sent quote past its valid-until date shows and totals as expired. A quote is never deleted and its number is never reused — there is no delete route, and the number comes from `number_counters` when the quote is created.
- A quote line keeps the product's name and unit price as they were when the line was added, so a later change to a product never moves a quote; `product_id` points at the product the line came from, and only active products can be added.
- `invoices` and `invoice_lines` hold the bill for one won deal. An invoice stores its number only once issued, and `number` is unique so two invoices can never share one. A draft's `number`, dates and tax columns stay empty until it is issued: the tax label and rate are read from the settings while it is a draft and written to the invoice at issue, together with the Bill to snapshot — the organization's name and billing address and the deal's contact name and email — so an issued invoice never changes. The stored `subtotal_cents` is the lines' sum; `tax_cents` and `total_cents` are stored at issue. A partial unique index on `deal_id` where the status is not `void` enforces one non-void invoice per deal on both databases. A line keeps `product_id` as a pointer only: its `description` and `unit_price_cents` are the snapshot, and a product's later change never touches a line.
- `payments` belong to an issued invoice. `paid_on` is a plain calendar date, like every date column here — issue dates, due dates and payment dates carry no time and no timezone, while `company_settings.updated_at` holds UTC. A payment's method is one of `bank_transfer`, `card`, `check`, `cash` or `other`. Deleting a payment is the only way it leaves, and the invoice's balance moves with it.
- An invoice's display status is worked out, never stored: `draft`, `issued` and `void` are stored, and `part paid`, `paid` and `overdue` come from the balance and the due date. A balance is the stored total minus the invoice's payments. The dashboard's aging buckets and the payments chart come from these same rows.
- Exactly one of `contact_id` / `deal_id` is set; `stage_change` rows are system-generated (read-only), written automatically when a deal's stage changes, e.g. "Moved from Proposal to Negotiation".
- Stage probabilities: New 10%, Qualified 25%, Proposal 50%, Negotiation 75%, Won 100%, Lost 0%. A manual probability persists until the stage changes, then resets to the new stage's default.
- Expected revenue = value × probability, over deals not in Won/Lost.
- Money stored in whole cents (integers) and displayed in US dollars, never as bare cents, such as `$49.50`. Product prices are a whole number of cents, zero or more and no more than 2,147,483,647 — what the integer column stores — shown with two decimals. Invoice amounts follow the same rule and always show two decimals, such as `$1,234.56`.
- A product's `active` flag is its archive state: new products start active, archiving sets it false and restoring sets it true. A product's name is unique ignoring case across active and archived products; the API enforces that on create and update.

## API (JSON, under `/api`)

- Every route refuses when nobody is signed in; the user behind a request comes from the checked sign-in — the Supabase token the way Render runs, the local sign-in on this computer — never from the request.
- `/organizations`, `/contacts`, `/deals`, `/activities`: list (with `q` search, sort, status/stage filters), create, update, delete (delete returns the counts and names of cascaded records for the confirmation dialog). A deal's update refuses a change of value while it has an invoice that isn't void.
- `/settings`: `GET` returns the company settings; `PUT` replaces them, checking every value and recording who changed them and when. The documents fields travel with it: `invoice_design` and `accent_color`, checked on both sides. `GET /api/settings/logo` serves the logo, `PUT /api/settings/logo` takes its type and its bytes, and `DELETE /api/settings/logo` removes it.
- `/products`: list (with `q` search, sort and a filter for archived products), create, update, archive and restore. Products have no delete route.
- `/quotes`: list (with the five status totals), one quote, create on an open deal, update a draft, and the send, copy, accept and decline actions, with the PDF at `GET /quotes/{id}/pdf`. Quotes have no delete route, and only a draft is changed.
- `/bills`: list (with `q` search over the supplier's name and the bill number, sort, a status filter and a supplier filter for an organization's page), create, update and delete, plus `POST /bills/{id}/paid` with the day the bill was paid and `POST /bills/{id}/unpaid` to undo it. A bill number used twice for the same supplier is a 400 with a clear message.
- `/invoices`: list (with `q` over number, organization and deal, sort, a status filter, and `deal_id` and `organization_id` for the deal and organization panels), create from a won deal, and `GET`, `PUT` and `DELETE` on one invoice — `PUT` and `DELETE` only while it is a draft. `POST /api/invoices/{id}/issue` takes the issue date, writes the number, the due date, the snapshots and the totals, and `POST /api/invoices/{id}/void` voids an invoice that has no payments. Every amount comes back from the backend, worked out from the lines.
- `/invoices/{id}/payments`: list as part of the invoice, record one and delete one. A payment is more than zero and no more than the balance, dated no later than today, and only an issued invoice takes one.
- `/invoices/{id}/pdf`: the invoice's PDF, made when asked for, named after its number and carrying the paid, overdue or void mark of the moment.
- Top-bar search: `GET /api/search?q=` returns organizations, contacts, deals and active products whose name contains the query, ignoring case — the same on SQLite and Postgres. Each match says which kind of record it is and its id, so the app can open it; a product match opens the Products page with that product shown, since products have no detail page. Archived products are left out. The per-table `q` search is unchanged, and quotes, invoices and bills are searched from their own tabs, not the top bar.
- `/dashboard`: aggregated figures for the charts, pipeline totals, recent activity, follow-ups, and both halves of the Money section — what customers owe, how much is overdue, the five aging buckets and the payments received in each of the last 12 months; and what is unpaid and how many bills, what is overdue, what is due in the next 30 days with the suppliers those bills name, and spending by category over the last 12 months, counted in each bill's paid month.
- `/deals/{id}/stage`: move a deal (stage + position); returns updated probability and totals. Accepting a quote moves its deal the same way and sets its value.

## Frontend

- Client-side routing to the seven sections, the Settings page, the Money tabs with the quote pages under `/money/quotes` and the invoice page under `/money/invoices`, and record detail pages for organizations, contacts, deals and invoices (organization: contacts, deals, quotes, invoices and bills lists; contact/deal: details + timeline newest first, with the deal's quotes and invoices panels below; invoice: the document, its payments and its actions); products have no detail page, and neither do bills, which live in the Bills tab and in the organization's bills panel. Signed out, every route shows the sign-in screen.
- **Top bar**: section navigation, the search box, and a menu under your initials with Settings, the theme choice and signing out. Money links to its tabbed page, and the areas add panels to deal and organization pages through `RecordPanels` — the quotes area's panels, the invoices area's panels and the bills area's organization panel — and neither page names the area that made one.
- **Settings**: one page with the company details form, a Save button and a line showing who last changed the settings and when; the saved values and the new line show at once. Below it, the Documents section — design, accent color and logo — with its own Save and a sample invoice beside it that updates as the choices change.
- **Documents**: a quote is created and edited in the wide dialog, with its form beside the live preview of the customer's document; the preview and the PDF share one layout, and the quote's page shows the same document with its actions and totals. An invoice's form and preview work the same way, and its page shows the document, a bar of paid against still owed, the payments with who entered them, and the actions a draft or an issued invoice allows.
- **Tables**: TanStack Table for search, sort, filters, pagination-free layout; one shared table component with add/edit modal and delete-confirm dialog; the Products table uses it with Archive and Restore in place of Delete and a Show archived control; the Bills table uses it with a status filter and Mark paid and Mark unpaid on each row; the invoices table uses it with no Add — invoices start on a won deal — Edit and Delete on drafts, and Void and Download PDF on issued invoices.
- **Charts**: Recharts — line (revenue won per month), bar (deals won per month), funnel/pipeline visual built from stage bars, a bar for the aging buckets and a line for the payments received per month, and the stacked spending-by-category bars.
- **Pipeline**: dnd-kit; each column keeps a `position` per card, dropped cards persist their exact slot, totals recompute from the store after each move.
- **State/data**: a small query layer (React Query) caching API responses; every mutation updates the cache so totals and lists move immediately.

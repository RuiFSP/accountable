# Improve the harness

Run this at Deploy, after the review's findings are settled — fixed, or accepted as non-blocking — and before the merge.

1. Look at what went wrong on this change: the review's findings, what the person corrected, what the checks caught — and what the checks missed. Read the review report and the last `npm run check` output, and name the gate gap behind each finding. Every gate stayed green on the dark-mode change while it broke its own AA rule, and again on products while a badge broke AA in light mode and the prices skipped the spec's cents; the company-settings checks passed while a UTC test compared against the local date, so don't take a green run as evidence the requirements held. A review that could not see the diff or run the checks is a finding about the harness, not just about the change. A gap you only name in step 6 recurs: close it in step 2 with a test or a rule, or say in step 6 why it stays open.
2. For a mistake that has happened twice, here or in an earlier change, add the correction to AGENTS.md or docs/REVIEW.md, or suggest a change to docs/STANDARDS.md for the person to make. Put it where it would have stopped the mistake: rules about writing the change go in AGENTS.md, rules about judging it go in REVIEW.md. If a tool can catch it, add it to the checks instead, generalized to the whole class — the badge check now covers every badge in both modes, not just the one the review named. A rule that only says "be careful" fixes nothing.
3. Map the review to REVIEW.md's labels — Important and Nits — before acting. The products review came back as Blocker/Major/Minor because the instructions named another scale, which left "fix the Important findings" ambiguous.
4. Run the full gate after the fixes, not just the tests around them. The products fixes passed their focused tests; the full run then caught the wider prices scrolling a 1024px page sideways. Start it when nothing else is in flight: a fix added while it runs makes its counts stale, and you run it again.
5. Remove anything out of date — counts, hedges and claims the fixes have since changed. Check the user-facing README as well as `docs/`: its feature list and run instructions drift when a change lands. The README claimed WCAG AA in both modes while light mode keeps its original, sometimes lower, contrast; it now matches the spec. A count comes from the run output or from counting the code, never from memory.
6. Record in docs/STATUS.md what the harness and docs now say, and which finding each change answers.
7. Improve this file, so that the next round makes a better change. Keep this as the last step.
